# 05 — Legal & Compliance

This document is **not legal advice.** Before launch, get a real Indian privacy/IT lawyer to review. But these are the issues that will shape product design from day one.

---

## A. Digital Personal Data Protection Act, 2023 (DPDP Act)

The DPDP Act + Rules 2025 were notified on **November 13, 2025**, with substantive obligations effective **May 13, 2027** (18-month grace).

### What applies to us

We process "personal data" of:
- The **user** (their resume, profile, job history)
- **Third parties** the user wants us to act on (referrer LinkedIn profiles, recruiter contact info)

### Obligations we must build for

1. **Consent UI on signup** — clear, granular, separate consent for: portal scraping, LLM processing, third-party data lookups (LinkedIn referrer profiles, Glassdoor sentiment).
2. **Purpose limitation** — only use the user's data for the job-search purpose stated.
3. **Right to access / correct / erase** — UI flow to download all user data and to wipe it within 7 days of request.
4. **Data minimization** — don't store more than needed; rotate logs.
5. **Breach notification** — incident response plan; notify within statutory timeline regardless of severity.
6. **No cross-border transfer** without compliance — if we send LLM calls to Anthropic/OpenAI in the US, we need consent + contractual safeguards (DPA with provider).
7. **Children's data** — don't allow under-18 signup; verifiable parental consent required if we ever do.
8. **Data Protection Officer** — required for "Significant Data Fiduciaries"; once we cross volume thresholds, name a DPO.

### Section 3(c)(ii) — publicly-available-data exemption

There is an exemption for personal data that has been "made publicly available by the data principal or by any other person under a legal obligation." This **may** cover scraping public LinkedIn profiles, but Indian guidance is **inconsistent**, and case law is undeveloped.

**Operational rule:**
- Treat all third-party personal data as if consent were required.
- Don't store referrer LinkedIn data permanently — fetch, use, discard.
- Always show the user *who* the agent is about to message and *what*; never auto-send to third parties without user confirmation.

## B. Per-portal Terms of Service

| Portal | ToS posture toward automation | Our approach |
|--------|-------------------------------|---------------|
| **Naukri** | Forbids automated scraping/applies. Account suspension is the standard penalty. | **Tier 2 only** — user's own session, user-initiated, user-confirmed submission. Never run bulk scrapes from server side. Document this clearly to users. |
| **LinkedIn** | Aggressive — `hiQ Labs v. LinkedIn` legal saga is well-known; LinkedIn actively bans automation. **Easy Apply API** is the legitimate path. | Use Easy Apply only via official integration. For referrer discovery, use the user's authenticated session and reasonable rate limits (≤30 profile views/hour, like a heavy human user). |
| **Indeed** | Has an **official Indeed Apply API** for partners. | Pursue API partnership. Tier 1 path. |
| **Foundit, Instahyre, Cutshort, Hirect, Apna** | Standard "no automation" clauses, less aggressively enforced. | Tier 2 — user-session, user-confirmed. |
| **Wellfound** | Lighter — single Apply button is essentially a public form. | Tier 1 / Tier 2. |
| **Greenhouse, Lever, Ashby** | Public job pages, public form posts. ATS owners don't really care; the *companies* using them might. | Tier 1 — direct form posts (within reason, rate-limited, not bulk). |
| **Workday, SuccessFactors** | Customer-of-employer dictates. Forms are gnarly anyway. | Tier 3 (manual) is often the only honest path. |
| **WhatsApp** | Personal WhatsApp automation = ToS violation; WhatsApp Business API = legitimate but heavyweight. | WhatsApp Business API for paying users. Personal WhatsApp = assist mode (drafts, doesn't send). |

## C. The "spam vs help" line

The whole product can become a **spamming machine** if we let it. We won't.

### Hard product rules

1. **Per-day cap on applications**: 25/day default, 50/day max with confirmation. Beyond that = degraded recruiter response anyway, so capping is also good for the user.
2. **No identical CVs to two roles at the same company.**
3. **No referrer DM without user approval** — every single one.
4. **Truthful CV only** — the rewriter rephrases and reorders, never invents. We have an automated "fact-check" pass that compares the rewritten CV against the source profile and flags any new factual claim.
5. **Watermark in PDF metadata** — "Generated by CareerOps India for [user] on [date]." Recruiters can verify if needed; transparency builds trust.
6. **Recruiter opt-out** — public page where any recruiter can request that their listings/profile be excluded.
7. **Public abuse report channel** — if we are causing portal-side problems, we want to know fast.

### Soft norms

- Don't auto-apply during a recruiter's likely sleeping hours from their timezone (looks botty)
- Avoid weekend submits to enterprise ATSs (recruiters don't see them till Monday anyway, just adds noise)
- Always include a real, distinct cover letter — generic cover letters are spam

## D. Liability surfaces

What can go wrong:
1. User account banned on a portal → **clear in-product disclaimer** at signup, opt-in per portal.
2. Recruiter complains about CV claims that exceed truth → **truthfulness pass + audit log** of every rewrite.
3. Third-party LinkedIn user complains about a DM → **user always reviews + sends, never the agent silently**. The user is the legal sender.
4. DPDP regulator asks for our processing inventory → **maintain ROPA (Record of Processing Activities) from day one**.

---

## E. The startup-friendly posture

- **Local-first MVP** sidesteps a lot of this — user's machine, user's cookies, user's intent. We're a "tool the user runs," not a "service that scrapes on behalf of users."
- **Open-source the core** (like Career-Ops did). Transparency = trust. Monetize hosted convenience layer.
- **Publish a public ethics doc**. Two paragraphs. Live URL. Update it.
